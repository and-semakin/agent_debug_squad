# v0.18.0 — task-level loop controls

Release preparation; the tag and published release are intentionally not created here.

## Changes

Workflows can select, review and consolidate a queue using the same local loop-control primitive. Version-2 tasks map declared verdicts to `proceed`, `continue`, `break` or `needs_attention`. Controls can appear at the head, middle or tail and gate whole nested subtrees, including independent internal roots.

Control decisions, skipped outcomes and closed passes are durable and auditable. Skipped work creates no backend attempt. Final dependencies use exact invocation contexts and never substitute an earlier successful result for a final skip. Graceful stop, override, retry and extension preserve their recorded contexts and idempotency. New phases pass backend preflight before attempt reservation.

Schema-4 API views expose control evidence, full paths, entered-pass counts, explicit skipped invocations and missing-result reasons. The one-shot summary also includes skip history and control decisions. Loopless version-1 workflows, confidence-threshold precedence and manual-agent behavior are preserved.

## Breaking changes and upgrade

- New loop workflows require `workflow.version: 2`. Move each legacy loop's `on_verdict` map to the named task's `control` field and remove `until_task`. Use a new submission request ID.
- All version-2 executions, including loopless ones, use snapshot schema 4.
- Finish or cancel active legacy loop executions with the previous binary before upgrading. Nonterminal legacy loops block startup; terminal legacy history remains read-only with `execution_supported: false`.
- Do not edit snapshots or replay backend side effects to migrate. Retain schema-4 state separately if rolling back; older binaries cannot resume it.
- A controlled loop whose actions all say `proceed` holds at its cap by default. Set `on_exhaustion: succeed` explicitly when that is intended.

## Publishing checklist

After the reviewed change is on `main`, verify the release commit's CI and ensure the checkout contains no unintended changes. Publishing requires a separate explicit request.

1. Create an annotated `v0.18.0` tag on that main commit and push it.
2. Watch the existing **Release** workflow; it runs formatting, vet, race tests and GoReleaser.
3. Verify these assets and `checksums.txt`:
   - `agent-debug-squad_darwin_amd64.tar.gz`
   - `agent-debug-squad_darwin_arm64.tar.gz`
   - `agent-debug-squad_linux_amd64.tar.gz`
   - `agent-debug-squad_linux_arm64.tar.gz`
4. Verify the downloaded native binary reports `v0.18.0` through `agent-debug-squad version`.

The next minor version is appropriate for this pre-1.0 breaking configuration and persistence change. Versions continue to come from annotated Git tags and GoReleaser; development builds remain `dev`.
