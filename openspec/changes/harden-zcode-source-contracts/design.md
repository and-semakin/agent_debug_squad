## Context

See [proposal](proposal.md) for motivation. [research](research.md) records the earlier investigation; its selected native/personal-API architecture is historical and superseded by this account-only revision. The source observations remain useful, but this design, proposal and delta specs define the current scope. Research applies to upstream `29628c9acdb81b703bbd4080c207a0e7ce5e276e`, not every binary labelled 3.14.3. No real protocol probe was run. Current source makes account authentication unavailable on the protocol-server entrypoint without another host, so the existing host remains necessary.

The adapter already has a Go NDJSON client, persistent session IDs, run-scoped permissions, recursive child polling and process-group termination. `host.cjs` does two different jobs: common host policy and unsupported internal registry/credential extraction. Existing installation and catalog code are already present. There were no active changes at initial inspection; integrate with those main capabilities instead of rebuilding their CLI, budgets or result envelopes.

## Goals / Non-Goals

**Goals:** prioritize Start allowance over Individual for the same requested model, preserve the installed-runtime account integration, and harden its lifecycle using source contracts.

**Non-Goals:** personal API providers/direct launch, provider/account creation, promotion activation, redeeming quota resets, OAuth refresh reimplementation, Team/BigModel/off-peak support, copied cipher, v4 execution or shipping a fork of the TypeScript runtime. No implementation or release in this planning change.

## Decisions

### 1. Preserve the installed-runtime account integration

Use one existing launch contract: command is Node, runtime_path is the installed CJS runtime, and host.cjs starts app-server. No integration option, native mode, personal API path or backend_session_mode field is added. Keep current machine defaults and explicit environment precedence. Resolve runtime/config paths against the same workspace in launch and preflight. Honor explicit provider paths and ZCODE_DATA_BASE_DIR without treating data roots, session storage and credential encryption identity as interchangeable. Keep structural extraction checks until a verified native host API makes them unnecessary; source publication alone does not remove the account-host obligation.

Add per-agent `plan_policy` with `fixed` (default) and `start-first`. Fixed preserves the existing Individual provider selection and Flash/low defaults; its safety gates are tightened as specified below, so compatibility is configuration/session compatibility, not a promise that every formerly admitted account state still runs. Start-first accepts only the Z.AI Start/Individual provider family and treats options.model as the requested model, preserving reasoning. Reject unrelated explicit providers rather than ignoring them. The policy authorizes using either of these two plans; it does not change desktop global selections. Provider changes occur through full modelSelection on subsequent session/send calls in the same persisted conversation, not through a new conversation or replay.

### 1a. Model-specific Start-first routing

Before each new Squad turn, the host resolves one account-bound eligibility snapshot. The native current Z.AI identity must match both plan auth sources; multiple stored credential keys are not evidence of the current account. Start uses ZCode JWT authentication, Individual uses its plan key. Extend the existing guarded credential boundary; do not expose either material to Go, YAML or artifacts or copy the cipher. When current identity cannot be established or a token requires unsupported refresh, fail auth-required and direct repair to ZCode. Do not implement login or pretend that rereading an expired JWT refreshes it.

The source-defined Start balance GET returns plans and per-model buckets with available_units, remaining_units, reserved_units, capabilities, entitlement IDs and expiry. It requires the real app_version and native endpoint/proxy policy. Use the bounded read policy in section 1c (a shared 15-second decision budget within the caller budget), no redirects to an unverified origin, bounded response and allowlisted normalized output. The host can use the native credential store plus this narrow source-defined read request; no whole services runtime is imported. Source fixtures must verify decoding and account identity binding before enabling this path. Account overlay must carry actual eligibility/model restrictions and the native builtin revision, not unconditional entitled/current claims. Individual availability must likewise remain account-bound; no assumption that a stored key proves entitlement.

Selection rules:

| Evidence for requested model | Decision |
|---|---|
| Active applicable Start bucket, valid period, positive spendable balance | Start provider, exact same model and reasoning |
| Model authoritatively absent from Start, promotion expired, or confirmed exhausted | Individual if that same model is available there |
| Remaining positive but available zero because reservations occupy it | Temporarily busy; bounded wait/recheck or explicit busy failure, not exhausted |
| Network/auth/schema error, ambiguous bucket ownership, missing numeric/time evidence | Unknown; fail safely without silently spending Individual |
| Neither plan supplies the requested model | Explicit unavailable-model error; do not substitute another model |

Match buckets using provider/model identity and documented normalization, not display names alone. Associate bucket/user_plan_id/entitlement_id with active plans; reject unsupported units or contradictory values. Multiple model buckets must not be added across incompatible units or counted twice. Respect server time paired with the response and plan/entitlement/bucket periods. A displayed 100% or model list entry is insufficient to prove spendability. available_units accounts for reservations; remaining_units is the UI's remaining balance and must not silently replace missing available evidence. A bounded refresh may resolve missing evidence; otherwise report unknown.

Use the precise coalescing/freshness policy in section 1c. Recheck at each new turn and confirmed quota-failure transition; crossing an expiry boundary invalidates evidence for the next selection, but does not trigger a timer-driven request or switch during an active native turn. Do not permanently mark Start exhausted: a new promotion/reset must regain priority. Parallel agents share an advisory snapshot, not an atomic reservation; only the service authoritatively grants budget. Log requested model, effective provider, decision reason and evidence timestamp, never raw billing/account/auth data. No promise of consuming the very last token is possible with concurrent users and reservations.

### 1b. Continue after a quota-exhaustion failure

Use the ordinary conversation behavior confirmed by the user: the failed native turn ends, then a new native turn sends a short continuation under the other provider. There is no attempt to switch a running model step or use Individual credentials against the Start endpoint. Keep the same backend session and requested model/reasoning. Send the fixed message `Please continue from where you stopped. Use the existing conversation and completed work; do not restart the task.` once, with a distinct inputId, after selecting Individual through the full modelSelection. Do not resend the original prompt or startup instructions.

This transition is allowed only for plan_policy start-first, an owned Start turn with an authoritative terminal failure and a verified quota-exhaustion classification, and an available same-model Individual selection for the same account. The classifier must use source/fixture-verified structured error evidence; a generic 429, auth failure, busy/admission code such as 3010, network timeout or arbitrary error text is insufficient. Refresh eligibility for diagnostics; a definitive typed exhaustion error is itself quota evidence, but uncertainty about Individual eligibility still prevents dispatch. A lost connection with unknown turn outcome never qualifies. Do not restart the process automatically to guess whether an ambiguous turn ended.

Keep this as one logical Squad run containing at most two native turns. The failed Start attempt remains visible as an intermediate diagnostic; it is not emitted as the final Squad failure before the decision. Give the continuation a fresh owned turn/input binding, retire old pending permissions/auth requests and reject late old-turn completions. Drain/stop positively owned descendant/background work from the failed attempt before continuing; if bounded cleanup cannot establish that it stopped, fail rather than overlap attempts. Keep the root conversation open. The final result comes from the continuation's owned completion, while streamed artifacts from both attempts remain available.

Allow at most one automatic Start-to-Individual continuation per Squad run; Individual failure ends the run without a loop or switch back. Share the original caller deadline and cancellation with both attempts, including eligibility and cleanup; do not grant a fresh run timeout. Cancellation/force reset before or during transition suppresses further send. A subsequent independent Squad turn re-evaluates Start preference normally. Record only safe transition evidence (from/to provider, reason, attempt/input IDs), not auth/billing bodies.

This avoids replaying the task at the orchestration layer; it cannot guarantee that a model will never choose to repeat a tool operation after reading the conversation. Tests must demonstrate persisted history and no adapter-generated original-task replay. The isolated protocol test must exercise failed turn -> same-session send with changed provider and fresh inputId; source-specific mismatch is an implementation failure to resolve, not a reason to silently fall back to resending the original task.

### 1c. Exact configuration, eligibility and scheduling rules

`plan_policy` is agent-only, deliberately not a machine backend key. Validate its type/enum and provider combination at YAML load, before preflight or run allocation; direct adapter construction must enforce the same check. Omitted policy is fixed. Fixed retains the currently supported provider `account:zai-individual-coding-plan` (including omission). Start-first accepts an omitted provider or exactly `account:zai-start-plan` or `account:zai-individual-coding-plan`; both explicit values designate the allowed routing family, not a pinned plan. Omission uses that same two-provider family. All other provider IDs are rejected. Model/reasoning defaults stay Flash/low; changing policy does not authorize model substitution.

Individual selectable evidence is the conjunction of (1) the relevant credential is resolved under the policy's identity rule, (2) a successful native-origin GET `/api/biz/subscription/list` yields an active Coding product with status `VALID` and inCurrentPeriod=true under the upstream decoder, and (3) after applying that account evidence, the live registry's selectable view contains the exact Individual provider/model and requested reasoning. Read the native registry service view through the existing guarded bridge; do not build another registry or invoke ListModels/connectivity inference. A raw builtin entry or lack of a disabledReason field is not proof of selectability. The subscription result certifies entitlement, not a model-specific remaining balance or successful future inference. Unknown registry shape/reasoning or malformed relevant subscription records means unknown, not available. A valid list with no active Coding subscription means unavailable. Fetch Individual evidence lazily only when selecting Individual (including fixed and quota continuation); an unavailable Individual must not prevent using a valid Start allowance. Cross-plan identity must still be consistent before any fallback.

The source decoder is [codingPlanEntitlement.ts](https://github.com/zai-org/ZCode/blob/29628c9acdb81b703bbd4080c207a0e7ce5e276e/packages/services/src/bigmodel/codingPlanEntitlement.ts); [codingPlanProviderAvailability.ts](https://github.com/zai-org/ZCode/blob/29628c9acdb81b703bbd4080c207a0e7ce5e276e/packages/services/src/model-provider/codingPlanProviderAvailability.ts) binds the Z.AI business origin and keeps Start/Individual entitlement queries independent. These are inspected source facts, not a live account verification.

| Limit | Chosen value and semantics |
|---|---|
| Entire eligibility decision | 15 seconds, including waits/queue, HTTP reads, registry projection and any recheck; earlier caller deadline wins |
| One HTTP attempt | At most 5 seconds and remaining decision budget; at most two attempts per endpoint per decision |
| Retryable reads | Only Start balance GET and Individual subscription-list GET; one retry after 250 ms for transport failure or HTTP 502/503/504, inside the same budget |
| No retry | Auth errors, other 4xx/429, malformed successful payloads, unknown business errors, cancelled requests; no generic protocol RPC retry |
| Reservation busy | One fresh Start balance recheck after 1 second, subject to the same two-attempt Start endpoint cap and shared budget; then routing_temporary_busy |
| Evidence sharing | Only within one Squad server process and identical account identity/credential generation, endpoint, effective environment and registry revision; no cross-squad daemon or persisted cache |
| Maximum evidence age | 1 second since request START, and never across account/config/expiry changes; a later decision cannot reuse an older response |
| In-flight joining | Join only a matching request started within the preceding second, each waiter retains its deadline; no waiter may extend the request/decision budget |
| Slow joined response | If older than 1 second at dispatch, usable only by its initiating decision; joiners must obtain their own eligible evidence within their remaining budget or fail unknown |
| Before quota continuation | After eligibility and old-attempt cleanup, require at least 5 seconds remaining on a finite original run deadline immediately before send; otherwise continuation_budget_insufficient; no-deadline contexts still honor cancellation |

The initiator's own response is not a shared cached snapshot: it is fresh for that decision on receipt, subject to expiry revalidation at dispatch. This avoids an endless refetch loop when a request itself takes more than a second. Every decision revalidates account/config identity before dispatch. Different endpoints can fail independently: exhausting the Start read retry/budget blocks a start-first turn even when Individual inference would work. No unknown-to-Individual option is added. The explicit escape is a future user-selected fixed run, which still checks Individual entitlement but does not depend on Start billing. Normally there is one Start read; choosing Individual may add one subscription read. Concurrency coalescing reduces bursts within a process, not across separate squads, so worst-case added eligibility latency remains 15 seconds per decision and failure remains possible under upstream load.

### 1d. Routing diagnostics and explicit retry boundaries

Use an allowlisted routing diagnostic with fields `requested_model`, `effective_provider` (only when chosen), `plan_policy`, `reason_code`, `observed_at` (UTC RFC3339 only when actual evidence exists), `evidence_age_ms` (when known), and attempt/input IDs when applicable. Unknown timestamps remain absent, not invented. Allowed outcome codes are `routing_start_available`, `routing_start_model_absent`, `routing_start_expired`, `routing_start_exhausted`, `routing_temporary_busy`, `routing_balance_unknown`, `routing_individual_unknown`, `routing_individual_unavailable`, `routing_model_unavailable`, `routing_auth_required`, `routing_continuation_started`, `continuation_budget_insufficient` and `routing_continuation_failed`. Existing wire/transport/cleanup error codes remain separate. No account identity, raw balances, environment values or auth material is included.

No automatic adapter replay after execution-outcome-unknown does not prohibit an explicitly requested workflow retry or manual resubmission. Workflow retries retain their existing fresh-conversation semantics and can repeat external effects; the one quota continuation is inside one task attempt/session, not a workflow retry or a newly admitted loop iteration. It shares the existing attempt's timeout/cancellation and must not bypass workflow pause/reset/stop handling.

### 2. Minimal host responsibilities belong in the Go duplex client

The common Go client services inbound requests throughout startup, create/resume, subscribe, send, polling and shutdown. It must not wait for the main Send event loop to begin. Use an always-running reader/router and a serialized run state owner; outbound response writing has its own bounded queue and cannot block cancellation behind an ordinary request. Bound frames to the existing 8 MiB; bound callback/event queues and fail explicitly on overflow instead of dropping a completion/permission event. Keep each RPC deadline at 15 seconds unless the caller expires earlier; bound write completion as well as response waiting.

Host dispatch table:

| Inbound operation | Squad policy |
|---|---|
| `session/requestRuntimePreferences` | Validate scope and bootstrap session association, return native search enhancements=false, memory=false and ask-user auto-resolution=false as current policy; never use upstream fallback defaults that enable question auto-resolution |
| `interaction/requestPermission` | Existing run-scoped endpoint and offered decisions, with generation/session/turn ownership and one terminal reply |
| `interaction/requestUserInput` | Explicit unsupported-interaction error and failed turn; never fabricate an answer |
| `interaction/requestProviderRuntimeHeaders` | Validated account-bound private auth request to the shim for the selected Start/Individual provider, never forwarded into artifacts |
| `interaction/providerRuntimeHeadersCancelled` notification | Invalidate matching pending request by process generation/workspace/session/request ID; discard late result |
| Any other required host request, including unsupported official MCP/browser operations | Bounded method-not-supported response and explicit failure; never hang or grant capabilities implicitly |

During create/resume the server can ask for preferences before the returned session ID is known. Permit one schema-valid bootstrap preference association for the outstanding operation, then require the returned snapshot's session ID to agree. This exception grants no auth or tool permissions. Reverse auth is only allowed for an established root/owned descendant, matching workspace and provider/model selection, and a current generation. Do not run blocking child enumeration inside the reader itself: queue an ownership resolution operation with a deadline while continuing to service responses/control traffic.

### 3. Keep the account bridge explicit

Move runtime preferences and general session policy into Go, retaining guarded native registry/credential extraction in JS. Bind auth requests to process generation, workspace, session/turn, provider/model and current account. Revalidate before replying, discard results after cancellation and never switch account identity mid-turn. Restrict new plan routing to Z.AI Start and Individual; do not infer Team/BigModel/off-peak support. Fixed retains the restricted unique-credential identity profile, but now requires fresh Individual entitlement and selectable-model evidence instead of the old cached availability plus hardcoded entitled/current overlay. It does not require the Start JWT or cross-plan current-account identity resolution. Start-first additionally requires verified current-account identity shared by both plans. Both policies require the expanded wire checks. These fixed overlay/wire safety changes are intentionally breaking for previously admitted but unverified states.

Keep actual account overlay revision and model restrictions consistent with evidence. An overlay receipt is not inference verification. Reject unknown/expired auth safely; native ZCode remains the place to repair login and activate offers. Use fixed diagnostics and lifetime redaction including rotated values. Secret auth material stays in shim-to-runtime pipes. This change still cannot remove all bundle extraction, eval or thunks for account use without another verified native host boundary.

### 4. Separate installation evidence from runtime compatibility

Installation remains the existing five-second, credential-free, non-executing check within the common preflight budgets. It checks Node, runtime readability and effective built-in config independently. It also checks required structural anchors without evaluating the bundle; that says compatible for extraction, not authenticated or wire-compatible. Do not start app-server, request --version, open credentials or inspect personal config in installation. Keep existing installation deduplication; model/reasoning/plan policy alone do not change local prerequisites.

During an actual owned execution startup, before creating/resuming a conversation, validate the selected legacy/session dialect. Use a source-derived bounded check set: `runtime/capabilities` is optional corroboration; methods required by Squad must reject schema-invalid empty parameters with the expected invalid-params code, not method-not-found. At this baseline parseParams precedes work in the selected session operations. Limit the set to verified parse-first create/resume/send/subscribe/setMode/stop/close/subagents/cancelBackgroundTask paths; do not probe valid IDs or create dummy sessions. An unexpected success is incompatible, never evidence of support. Complete the set within one 15-second startup budget, not 15 seconds per method. The existing host does this in its already-owned runtime before session work. No auth or account callback is authorized by probing.

These checks establish method/schema availability, not behavioral negotiation or exactly-once semantics. Validate snapshot wire identity, session IDs, subscription responses and event shapes at each subsequent boundary. Accept unknown additive fields; reject missing/invalid critical fields or unsupported dialects. No v4 hello is sent on this legacy connection. A separate future v4 change would need topic ACK/frame/replay semantics, not a renamed integer.

### 5. Turn identity, streaming and recovery

Keep one active run per adapter. Maintain process generation, session ID, input ID and owned turn ID. Subscribe before send; tolerate valid events arriving before the send response by buffering within bounds. Acceptance alone cannot succeed. Bind `turn.started` to the submitted input; only a matching owned terminal success with nonempty new response can complete. Ignore unrelated historical/foreign terminal events, deduplicate known event identities, and fail contradictory terminal results observed before finalization. Stream allowlisted non-secret event projections; final message comes from the owned terminal response, never old snapshot text. Preserve source event IDs/sequence when available; do not invent ordering evidence.

On broken transport after possible write/acceptance, return a distinct execution-outcome-unknown diagnostic, preserve the known session ID and streamed artifacts, and do not resend. There is no established general durable inputId deduplication guarantee. Ambiguous transport recovery may resume on a later explicitly requested turn; it does not replay the prior prompt, bootstrap instructions or permission decision. The separately defined confirmed-quota continuation is a new native turn after a known terminal failure, not transport recovery. Only the HTTP eligibility GET operations enumerated in section 1c may be retried automatically under that policy. No protocol RPC, including a session read or private factory call, receives an automatic generic retry in this change. Do not restart/replay during an active turn.

Preserve the existing backend session ID and reset semantics. Switching account providers under start-first must retain the same account and conversation, and pass the complete selection for every new input. Do not silently switch model or reasoning to satisfy a cheaper plan. No new session-mode persistence is needed.

### 6. Bounded descendants and background cleanup

Fix resume baseline traversal to include all historical descendant pages and nested descendants; a baseline read of only the first page must not claim future ownership. Cap traversal at 100 pages and 10,000 unique descendants per observation; detect repeated/cyclic cursors and cycles in ancestry. Exceeding a cap is an explicit incomplete-ownership failure, not silent success. Correlate newly observed child work with the active root turn where the wire supplies evidence; identity or liveness alone is insufficient for historical child permissions. Unknown ownership is denied.

Track background bash/work tasks independently of child sessions using source-derived legacy snapshot/event fields. Parent completion does not imply background completion. Stop the root, cancel known owned background tasks through the owning runtime, stop/close owned descendants where required, close the root, then close stdin and terminate the owned process group if necessary. All final Squad-run terminal paths share a five-second cleanup deadline, including a blocked writer and a leader that already exited. Graceful calls share two seconds; process termination/reaping uses the remaining budget. Never target processes by executable name or kill the user's desktop/other ZCode sessions. Do not claim to reclaim deliberately daemonized external work beyond observed ownership/process-group controls.

A cleanup failure prevents clean success; retain final text as evidence with an explicit cleanup failure. Cancellation remains cancelled even if a late completion arrives. Clear pending permissions/auth on every terminal transition. Orchestrator restart must not blindly kill a persisted PID that may have been reused; this change does not introduce such PID cleanup. Owned process-group tests establish what can be bounded on supported macOS/Linux.

### 7. Catalog and common interfaces

Keep `ListModels` session-free and configuration-read-only; return unsupported `read_only_catalog_unavailable` at this source baseline. Source ModelCatalogPort fields define future mapping expectations only. Do not create/resume a conversation, call the agent ListModels tool, send provider connectivity requests, initialize a potentially writing registry or use old session settings as a full catalog. Keep the common report status, inference_verification, budgets, hidden policy and secret filtering unchanged. This is a narrow ZCode amendment to the already implemented catalog work.

Use existing diagnostic hooks with safe codes for integration, dialect, installation-vs-runtime incompatibility, auth-required/unavailable, malformed message, unsupported interaction, transport loss, execution outcome unknown and cleanup failure. No raw auth callbacks, registry/config objects, proxy URLs or arbitrary runtime stderr enter public logs/artifacts. This tightens the current raw stderr path; retain fixed summaries and bounded safe operational provenance.

### 8. Contract verification without paid work

Check in synthetic fixtures with provenance (source commit, path/symbol and dialect); do not check in real account snapshots or copy the full schemas/runtime. Fixture coverage includes both JSON request-ID types, invalid params/errors, preferences during create/resume, permission options, provider cancellation, send ACK ordering, streaming/completion/failure, subagent pagination, background tasks and EOF. Include a source-review checklist for regenerating fixtures when upstream changes. Fixtures derived manually from schemas are labelled source-derived, not captured live traffic.

The integration harness uses a separately provisioned compatible CJS artifact, temporary HOME/data/storage/workspace, synthetic provider files, denied network, and filesystem write auditing outside the temporary root. Never fetch/build upstream as a test side effect. Exercise method probes and create/resume/subscribe/stop/close with no send/inference; deny all auth and unsupported callbacks. This harness proves lifecycle/config behavior for its tested artifact only. A stub model transport can exercise send/stream/permissions in fake protocol tests; no default test may require paid credentials. When native resources are unavailable, report the integration test as skipped and do not call it passed. The hardened account path requires recorded isolated protocol evidence. Start-first additionally requires source-derived billing/auth fixtures and a separately authorized read-only account check before claiming live account compatibility; no inference is needed for that check.

## Risks / Trade-offs

- Private account integration remains bundle-coupled; structural guards and source fixtures reduce mistakes but do not create a public stable API.
- Start balance read failure is not exhaustion; fail closed rather than silently consume paid quota. Explicit fixed selection avoids the Start balance dependency, but still requires fresh Individual subscription evidence. A subscription-list outage blocks fixed turns and any selection or continuation through Individual; it does not block an independently eligible Start turn because Individual evidence is fetched lazily.
- Individual selection now depends on the subscription endpoint even when inference itself is healthy, adding network latency within the fifteen-second eligibility budget. Retain only the one-second process-local sharing defined in section 1c; deliberately reject a longer subscription-evidence TTL or stale-cache fallback to avoid admitting a subscription whose eligibility has changed. This availability/latency cost is an intentional fail-closed trade-off.
- Billing buckets and reservations can change concurrently; selection is advisory, not an exact token-spending guarantee.
- Plan membership is not full model-catalog evidence; keep the general catalog unsupported until its own safe boundary is verified.
- Automatic continuation is bounded to one new native turn after confirmed quota failure. Preserve conversation/effects and never replay the original task; model-chosen repeated actions cannot be ruled out absolutely.
- JWT expiry/current-account resolution adds work beyond the previous Individual-only key flow. Do not ship start-first based only on screenshots, cached entitlement or a guessed credential key.

## Migration Plan

Existing configurations retain fixed-plan selection and persistent session IDs, but fresh Individual overlay evidence and wire checks can now reject previously admitted states; this is an intentional safety migration. Opting into plan_policy: start-first enables model-specific routing for future turns without changing desktop subscriptions or selecting a different account. Removing the option restores fixed behavior on the next turn; it never replays a failed turn; start-first alone permits the bounded new continuation described above. No direct/native launch option or session-mode field is introduced.

For fixed users, each dispatch now requires fresh subscription-list evidence, subject only to the bounded process-local sharing in section 1c. A readable key and cached availability no longer permit offline admission: subscription-service failure blocks the turn even if the inference endpoint is healthy, and eligibility may add up to fifteen seconds within the caller deadline. Fixed does not read Start billing. Removing start-first therefore bypasses Start balance failures only; it does not bypass Individual subscription verification. A valid Start selection remains independent of Individual subscription-service availability.

Implement the three review milestones below in dependency order; routing and continuation depend on the hardened host/lifecycle foundation. Verify Start auth and balance access with isolated synthetic fixtures; a live read-only account check must be separately authorized because prior investigation did not read credentials. Do not claim it has already happened. Document the distinction between a new continuation turn and replay, the one-transition limit and remaining model-level repetition risk. Finish gofmt, go vet, race tests and strict OpenSpec validation before implementation handoff/archive.

## Review milestones and disposition

Keep one change with three separately reviewable implementation milestones: A — synthetic contract fixtures, identity binding and host/lifecycle safety (tasks 1 and 3, plus the isolated base harness); B — billing response decoding, live registry eligibility and account routing (tasks 2.1–2.5 and common integration); C — quota continuation and end-to-end verification (tasks 2.6–2.8 and remaining documentation/checks). Each milestone must pass its relevant tests and be reviewed before the next depends on it; archive remains after all requirements pass. Installation/catalog edits are narrow integration boundaries, not separate product features. The harness validates these changes and is not independently shippable functionality. Splitting into several OpenSpec changes is therefore not adopted in this revision; implementation must not be one unreviewed bulk patch.

Review points 1–2 are resolved by explicit fixed safety migration and the three-part Individual eligibility rule. Points 3–5 have user-visible fail-closed behavior, numeric budgets and continuation deadline admission. Point 7 adds cancelBackgroundTask to the parse-first probes (its handler parses before session lookup), without claiming method presence proves every session runtime supports cancellation. Point 8 removes unchanged modified requirements. Points 9–12 are covered by configuration/failure scenarios, exact timing/provider semantics, diagnostic codes and explicit workflow retry documentation. No live account requests were performed for this revision.
