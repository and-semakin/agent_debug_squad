## Context

See proposal.md for motivation. At planning time (2026-09-28), `openspec list --json` returned no active changes. The current skill is a single `SKILL.md` with portable name/description frontmatter. README recommends manual copying. `internal/selfupdate.Client.Install` extracts only the executable; `cmd/agent-debug-squad/main.go` performs release checks, replacement and `syscall.Exec` for `serve`. Explicit `update` currently accepts no flags, and development builds reject it. GoReleaser builds CGO-free macOS/Linux AMD64/ARM64 binaries with injected version/commit/date. There is no existing skill ownership state or self-update capability spec.

Related contracts remain intact: backend-installation checks never install software; backend-config is a startup snapshot; model discovery stays read-only; workflow-lifecycle forbids automatic updates in `run`. This feature manages the instructions of the human-facing facilitator, not the workers named in YAML. Claude Code is therefore a valid skill host despite not being a Squad backend; `fake` is not a skill host.

Read-only local version probes found Codex CLI 0.156.1, Claude Code 2.1.228, Cursor Agent 2026.09.23-86fc751, OpenCode 1.18.30, Kimi Code 2.1.1 and ZCode desktop 3.14.3. No relevant directory override was set in the research process. These establish the installed generations, not proof that each host loaded a test skill; no user installation was modified and no model/session was started. Documentation may describe newer hosts, so resolver fixtures and a manual discovery checklist must distinguish documented behavior from an end-to-end compatibility claim.

## Goals / Non-Goals

**Goals:** offline reproducible bundle delivery; explicit ownership; recoverable replacement; honest partial outcomes; deterministic selection that avoids unnecessary copies; compatibility evidence that can be updated independently of backend adapters.

**Non-Goals:** discovering the calling agent from its parent process; scanning the entire home; enabling disabled skills; rewriting host configuration; installing every backend's skill; reconciling marketplaces; cloud/SSH deployment; changing running conversations; synchronizing during workflow execution; native Windows support. WSL uses its Linux home and filesystem, not Windows host directories.

## Decisions

### 1. One canonical portable payload, embedded at build time

Add an embeddable Go package under `skills/`, so `go:embed` can include the canonical `agent-debug-squad` subtree without `..` patterns or copying it into a second source tree. Include hidden resource files deliberately with `all:` semantics and validate the allowed source inventory. Reject symlinks, special files, traversal, reserved receipt names and case-fold collisions at build/test time. Resources are addressed relative to the installed skill; no repository or developer home paths are required. Frontmatter stays at the common `name`/`description` subset (description <=1024 characters); host-specific optional resources, if added, must be inert to other hosts. Keep SKILL.md below 100 KB for ZCode. Do not insert build-specific frontmatter or mutate tracked version strings.

The bundle identity is `sha256-v1` over sorted UTF-8 slash-separated relative paths, each encoded with byte length, file size, normalized executable bit and SHA-256 of exact bytes, preceded by a domain/version separator. Ignore timestamps, ownership and directory modes; reject duplicate/case-colliding paths. Specify an unambiguous length-prefixed byte encoding and golden vectors in implementation. The same source bundle has the same identity across all release architectures. Build provenance (normalized vMAJOR.MINOR.PATCH or dev, commit, date) is separate from content identity. Embedding contains all resources, including later additions and deletions; an archive sidecar is unnecessary and can drift from the executable.

### 2. Explicit commands and targets

```
agent-debug-squad skill install --agent codex --agent cursor [--json]
agent-debug-squad skill install --path /absolute/skills/agent-debug-squad [--adopt] [--json]
agent-debug-squad skill status [--agent NAME ... | --path DIR] [--json]
agent-debug-squad skill sync [--path DIR] [--allow-downgrade | --allow-dev] [--json]
agent-debug-squad update [--json]
```

`--path` always means the exact skill directory, never its parent; basename must be `agent-debug-squad`. Install requires repeated known `--agent` OR one absolute `--path`; no default all-agents installation and no interactive prompt. `--adopt`, `--allow-downgrade` and `--allow-dev` are also accepted on install, with the latter two mutually exclusive. Unknown agents, relative paths, missing selectors, incompatible flags and extra operands exit 2 without writes. Custom paths cover isolated profiles, project copies and agents without presets; they promise delivery, not host discovery. `sync` without selector targets every registration, `sync --path` requires an existing registration, and never installs a new target. `status` defaults to registrations plus bounded known user-root observations; it never writes, locks exclusively, repairs or launches host CLIs. A missing registry reports not_registered, not permission to adopt.

No `update --no-auto-update` flag is added: it is contradictory for an explicit update and remains invalid. Existing `serve --no-auto-update` and `AGENT_DEBUG_SQUAD_NO_AUTO_UPDATE=1` suppress both automatic release checks and automatic skill sync. They do not suppress explicit `update` or `skill sync`.

### 4. Ownership, backups and reconciliation

Use `~/.agent-debug-squad/skill-management/` (0700) independently of backend settings and workspace state: `registry.json`, `lock`, `transactions/`, and `backups/`. Registry schema 1 has a monotonically increasing generation, canonical absolute destination, destination UUID, selected host labels, recorded discovery root, bundle hash, file list with prior bytes hashes/executable bits, installed-from and last-verified-with build metadata, and greatest accepted release version with its accepted release bundle hash. File contents are never in diagnostics. An in-tree reserved `.agent-debug-squad-skill.json` receipt identifies the registration/transaction and expected bundle; it is not itself payload and cannot prove ownership without the matching registry entry. Do not automatically reconstruct a missing registry from receipts. Corrupt/unknown schema is a hard failure, not an empty registry.

An absent destination can be installed; an existing unregistered directory requires `--path ... --adopt`, even if byte-identical. Adoption requires a regular SKILL.md declaring exactly `agent-debug-squad`, a safe tree, and a verified full backup before any mutation. It enrolls only paths present in the new bundle; unrelated historical files stay unowned and visible with a diagnostic. Adoption is not permission to prune unknown legacy resources. Known plugin-managed roots are rejected, including with adopt; a plugin must be detached/exported first to avoid dual ownership.

For registered destinations, compare actual files, the previous manifest and embedded desired tree. Replace all managed files, remove previously managed files absent from the new tree, and keep unowned files byte-for-byte. Before replacing/removing locally modified managed files, save a verified archive of the entire old tree (including unknown files) outside skill discovery roots. Also back up a damaged/missing receipt before repairing it. If backup creation/verification fails, leave the destination unchanged. An unowned file that collides with a newly bundled path, or a file/directory structural conflict, blocks that destination; moving the conflicting file is an explicit user action, not an automatic adoption extension. Unknown files alone do not prevent updates and never become owned. Report backup location and preserved unknown paths. Backups use private archive files, never loose SKILL.md copies; no automatic backup pruning in v1.

A missing registered tree is repairable. A receipt with a different UUID or an unexpected tree type is `ownership_conflict`; a missing/invalid receipt can be repaired only for an otherwise valid registry-owned safe directory, after backup. Registry loss requires explicit adoption, preserving evidence. Metadata-only upgrades with identical payload update verification/release authority without rewriting SKILL.md or claiming it changed.

### 5. Recoverable per-destination transactions and filesystem boundaries

Use an OS advisory lock, following existing Unix flock semantics, for the private registry across all managing processes. Fail promptly with `busy`; never use PID age to break a live lock. Registry mutations, destination validation and commit decisions occur under this lock. Read-only status sees the last atomically committed registry and reports pending journals; it does not wait indefinitely. Separate executable-update locking, keyed by canonical executable path under the private management root, covers release check/install/handoff; acquire executable lock before registry lock and never the reverse. Close/release locks on cancellation and process death; do not hold the registry lock across downloads or child execution.

Reject symlink destinations, symlinks anywhere below them, special files, hard-linked regular files, path traversal, nested/overlapping destinations and paths overlapping registry/backup/staging roots. Canonicalize existing ancestors once, record their identity, and use directory-relative no-follow operations plus identity rechecks; a symlinked ancestor may resolve to a stable canonical directory, but a changed ancestor cannot redirect later writes. Validate manifest paths before reading/deleting them. Reject group/world-writable mutation parents and unsupported filesystems rather than claim protection against arbitrary hostile same-user races. The threat boundary excludes a malicious process with the same user credentials; advisory locks coordinate Squad processes, not arbitrary editors. Recheck the observed tree immediately before commit and abort if an external edit is detected.

Create the full replacement tree and pending receipt in a private staging area on the destination's filesystem, outside all known/registered discovery roots. Prefer a private transaction directory beside the discovery root, never inside it. If no safe same-filesystem staging location is available, fail without writes to the live tree. Verify contents and preserved files, fsync them and durable journal intent, then publish using atomic directory exchange on supported macOS/Linux filesystems; first installation uses atomic no-replace rename. Do not degrade to in-place copying or a remove-then-rename gap if exchange is unavailable: return `atomic_replace_unsupported`. Isolate platform primitives behind build-tagged helpers; a focused `x/sys/unix` dependency is acceptable if needed with CGO_ENABLED=0. No symlink generation-pointer install is used, even though some hosts support links, to avoid a universal scanner/link guarantee.

After exchange, fsync parent directories and atomically publish the updated registry using write/fsync/rename. Tree and registry are not one filesystem transaction: a durable journal with old/new hashes, UUID, generation and staging identities closes this gap. Before any later mutation, recover pending transactions by inspecting receipt and actual hashes: finish the registry commit when the new tree is published and matches; abandon an unpublished stage when old state still matches; retain both states and report `recovery_conflict` when neither matches. Never replay blindly or overwrite post-crash edits. Clean only verified transaction-owned staging files after registry commit; keep user backups. Cross-volume backup copying is allowed, but must complete and verify before publish.

Atomic exchange guarantees an entire old or new tree at the destination pathname, not a snapshot across multiple reads by an uncooperative agent. A reader that opened a file before exchange may still see old contents. A crash can leave a pending journal, never a partially copied live managed tree. Cancellation before publish abandons staging; after publish finish the small commit/recovery bookkeeping before returning, without starting another target. Batch operations commit independently; failures do not roll back successful destinations or stop unrelated targets unless cancelled/global registry failure. There is no global transaction with executable replacement.

### 6. Version authority and update handoff

Release versions come only from existing build metadata, normalized for comparison; content hash decides payload drift. A higher accepted release is an authority floor even when the payload stayed identical. An older release cannot automatically rewrite or repair a destination owned by a newer release. Explicit `skill sync --allow-downgrade` (or explicit install to an already registered path) permits replacement and resets that destination's authority floor to the requested version; backup is mandatory for a differing bundle. Same release with a different bundle is `release_identity_conflict` and needs a correct release binary, not a downgrade override. A dev binary can inspect status but only install/sync with `--allow-dev`; dev never auto-updates or auto-syncs. Dev writes record their hash and retain the last release authority floor; a release at/above that floor can restore its bundle with backup. Multiple installed Squad versions share this registry, so stale executables cannot oscillate managed copies.

Refactor the main CLI coordinator, not backend adapters. Explicit `update` checks the release and reports the binary outcome, then synchronizes registrations. No newer release (or a network/check/download failure before executable replacement) still attempts offline sync using the current executable's bundle; the binary failure remains an overall failure. An ambiguous replacement outcome skips old-image sync and reports uncertainty with a retry using the verified installed executable. After replacement, synchronizing must run in the installed executable resolved by the updater, not in the old process. Use a child invocation with a 60-second deadline (or the earlier caller deadline) of the public `skill sync --json` and verify reported build version/hash against the expected new release; the old parent aggregates its JSON and never substitutes its old payload. Serialize competing executable updates through this handoff. Child failure leaves the new binary installed, marks skill sync failed/unknown and gives an explicit retry command. No automatic binary rollback or backend launch occurs. Manual binary installation is reconciled by explicit sync or the next eligible serve startup.

For `serve`, automatic update and offline reconciliation finish before config/backend startup. On replacement, run new-binary sync and then re-exec the new binary once with a private one-use marker to skip the duplicate startup update cycle; do not implement the marker by setting the public opt-out permanently. Without replacement, run local sync even if remote checking failed or no upgrade exists. Automatic skill failures warn and allow service startup; they never become backend preflight failures. If re-exec fails, fail startup rather than run an old process against newly synchronized instructions. Already running Squad sessions are never restarted by another process's update; their metadata/session continuity remains as it was. `run`, `models`, `version` and skill status have no implicit sync.

### 7. Small, useful reporting surface

All skill commands and `update --json` emit a single schema-versioned envelope to stdout; human diagnostics go to stderr in JSON mode. Fields: `schema_version:1`, `program` (version/commit/date/bundle_hash), `status` (ok/partial/failed), `binary` for update (before/after/status), sorted `destinations`, `observations`, and optional global `error`. Destination fields: path, selected_agents, before/after hash and provenance when known, state/action, stable diagnostic code, changed boolean, reread_required boolean, preserved_paths, backup_path and retry command when applicable. No payload text, credentials or raw environment dumps. Escape terminal control characters in human paths. Status verifies actual file hashes; it does not trust receipt alone. Distinguish not_registered, current, outdated, missing, modified, conflict and pending_recovery. With no registry, update says no managed skills and suggests install, never says skills updated.

Skill commands exit 0 for satisfied requested state (including no-op sync), 1 for drift/status conflicts/operational or partial failures, 2 for invalid arguments. Status with no registrations is a successful inspection with explicit not_registered; no write occurs. Explicit update keeps its existing operational failure exit 2, now also for partial skill failure, while 0 means both binary action and requested sync succeeded. Serve warnings do not change its existing successful startup behavior. Metadata-only changes report changed=false and do not require reread. Changed payload or repaired files report the running/installed program version, absolute SKILL.md path, backup when present and: “Skill updated. Please reread <path> before continuing; refresh or restart your agent if needed.” This is a notification, never a claim to reload agent context.

## Risks / Trade-offs

- Host scanner rules change → small documented resolver table, source links and fixture tests; custom exact path remains available. No host-version probe is needed during automatic sync because destinations are already frozen.
- Multiple tools see the same name → reuse registered shared copies where valid, report collisions and unknown precedence, never silently remove unregistered copies.
- Local edits and archives consume disk → preserve and disclose backups; manual pruning only in this version. Prefer external machine configuration over editing the managed skill.
- Native exchange is unavailable on some mounts → fail that destination safely with a retry/move instruction. Verify both supported OS/architectures and keep archive builds CGO-free.
- Registry and tree commits can diverge on crash → intent journal, identity/hashes, recovery and explicit conflicts; no unsupported claim of global atomicity.
- Docs exceed installed host versions → presets describe documented local roots; full host loading and disabled/plugin precedence remain external to the filesystem success guarantee.

## Migration Plan

1. Ship embedded content and CLI support in a normal release; do not discover-and-install on first startup. A missing registry leaves manual installations unchanged and prints setup guidance.
2. Replace README copy instructions with explicit agent selection and custom-path/adopt examples. Explain shared visibility and exact path semantics before migration.
3. For an existing manual copy, run status, select its exact path, explicitly adopt after reviewing the backup/preservation policy; migration creates a verified backup and preserves unknown files. Do not touch plugin-controlled copies.
4. Subsequent update/eligible serve starts reconcile only the registrations. A failed destination is retried with `skill sync --path <dir>` after resolving its diagnostic.
5. Rollback of the executable alone leaves skill state intact. Use the older binary with explicit `--allow-downgrade` when intentional; restore local edits manually from the reported backup. Never replace a published release tag or hand-edit version constants.

No unresolved product decision blocks implementation. Exact platform syscall wrappers and encoding golden vectors are implementation details constrained by the contracts above; unsupported filesystems have a specified safe failure rather than an open fallback decision.
