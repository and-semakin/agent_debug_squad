## Context

See proposal.md for motivation. Observed implementation:

- `AgentAdapter` has Init/Send/Recover/Reset but no prerequisite contract. Codex, Cursor and Kimi resolve `command` inside Send, defaulting to `codex`, `cursor-agent`, and `kimi`. `exec.CommandContext` resolves a bare name before `cmd.Env` is assigned: current resolution can disagree with the child PATH.
- Codex/Cursor/ZCode environment builders can return nil, which exec interprets as full ambient inheritance; Kimi also explicitly returns nil when both option lists are empty. Even a nonempty inherit_env list can produce nil when no named variable exists. A non-nil environment slice is explicit, including an empty slice. Checks must preserve these actual launch semantics, not assume Kimi is the only ambient case. ZCode uses Cursor's environment builder and defaults to `node`; its bundled `host.cjs` reads a desktop runtime, discovers minified structures, compiles it, reads account data and starts app-server. These phases must be split for a credential-free probe.
- `orchestrator.New` initializes every configured manual adapter. OpenCode Init creates an HTTP session, so unused OpenCode currently affects startup. `SubmitRun` persists a run before starting a worker; `SubmitOwnedRun` initializes a fresh adapter after reservation. `workflow.Manager.Create` validates/hash-checks then saves a running execution; recovery can schedule automatically.
- Machine defaults merge in `agentSpecWithDefaults` and on recovered owned runs. Persisted agents intentionally exclude machine settings. Machine configuration loads once per server; ambient inherited values are read at dispatch.
- There is no agent/task enabled switch in the current schema. `ephemeral` does not disable an agent. Published Squad binaries target macOS/Linux AMD64/ARM64; native Windows support is not promised.
- The local baseline 7d21ef5 has external-only OpenCode. The archived managed OpenCode change in c06b at eedfa95 supplies managed-by-default, external selected by effective base_url, proxy/no_proxy and snapshot:false behavior and owned server lifecycle. This design consumes that resolved contract, including its failed-start latch, without implementing a second supervisor. Main at b78b530 also contains the one-shot run command (f584713). Read both revisions before implementation; no rebase or code changes are part of this artifact revision.

## Goals / Non-Goals

**Goals:** cheap local prerequisite evidence before work; complete actionable failures in one pass; consistent check/launch resolution; safe retry and lifecycle serialization without a second scheduler.

**Non-Goals:** proving authentication, model access, billing, arbitrary launcher internals, every dynamic shared-library dependency, or all OpenCode API compatibility. No automatic installation, backend CLI version probing, model calls, or backend session creation during installation checks. Judge setup and classification remain their separate existing contract.

## Decisions

### 1. Mandatory adapter method, small shared result vocabulary

Extend `AgentAdapter` with:

```go
CheckInstallation(ctx context.Context, input domain.InstallationInput) domain.InstallationResult
```

`InstallationInput` contains the absolute WorkspaceDir and one captured ambient environment slice. The adapter already holds the normalized, machine-merged AgentSpec. The explicit input avoids mutable global environment and passes the working directory before Init. Shared types live in domain (adapters' concrete packages cannot import their parent factory).

`InstallationResult` contains status (`ready`, `not_required`, `failed`) and all `InstallationIssue` values. Each issue has component (`executable`, `interpreter`, `runtime`, `provider_config`, or `platform`; readiness uses `service`), stable code, safe message and installation links. Expected failures, including timeout/cancellation, are data rather than an early return error so independent components can be collected. Unexpected internal failure becomes `check_failed` with a fixed public message. The coordinator attaches backend and sorted agent names and wraps the report in a typed `PreflightError` for errors.As. It must never interpolate raw subprocess, URL, environment or filesystem errors into the public message.

Shared resolver/probe code belongs in a small `internal/preflight` package importing domain only. Adapters retain knowledge of their own dependencies; the factory must not grow a second switch that describes their installation requirements. Factory construction is side-effect-free. Fake explicitly returns not_required; external OpenCode returns not_required locally, not a synthetic CLI success.

Alternative: optional interface assertion would silently allow a new backend to skip the gate. Mandatory conformance forces implementations and test doubles to state their behavior.

### 2. Effective launch resolution is shared with actual spawning

Use one adapter-specific launch-plan builder from both check and Send/server startup: effective command, absolute workspace, child environment and runtime/config paths. Capture the environment once per operation and retain that plan through its associated launch; don't resolve twice against different PATH values. Admission plans are discarded after admission; each later dispatch builds a new one. Materialize a nil launch environment as the captured ambient snapshot before checking PATH and launching; preserve a non-nil explicit environment as-is. Managed OpenCode instead uses its own baseline allowlist/runtime-owned environment snapshot. Never force it into the CLI builders' ambient rules.

An explicit command is one executable token, never shell syntax; spaces within a path are literal. Names search only the effective child PATH. Missing/empty PATH produces not_found with guidance to inherit/set PATH or configure an absolute command. Never implicitly search the current directory: ignore empty PATH elements and reject relative PATH elements as invalid_search_path; users can use explicit `./tool` instead. For bare-name resolution, validate the entire PATH first: any relative element rejects the lookup even if an earlier absolute directory contains the executable. Explicit paths do not inspect PATH unless an interpreter itself needs name resolution. Absolute PATH entries are searched in order. Commands containing a path separator resolve directly, with relative paths based on the workflow/manual workspace (also cmd.Dir), not the server launch directory. No shell, tilde or variable expansion. A bad explicit name/path never falls back to a backend default or another alias.

Follow symlinks and accept a usable regular target; broken links/loops, directory targets, inaccessible components and missing executable permission fail. On macOS/Linux check effective-user execute access, not only whether any execute bit is set. Resolve known shebang interpreters (absolute interpreter and `/usr/bin/env NAME`, including the simple `-S NAME ...` form) under the same child environment; reject an unparseable shebang as unsupported_launcher rather than claim interpreter coverage. Bound interpreter recursion and detect cycles. Do not execute arbitrary wrapper bodies to infer hidden dependencies. No hard dependency on Node/Python for self-contained CLI distributions; inspect the actual launcher instead.

This intentionally corrects parent-PATH lookup. Cursor's documented current command is `agent` while this repository defaults to `cursor-agent`: retain the existing default and suggest setting command to the installed official launcher; no silent alias fallback or unrelated default rename.

### 3. Backend-specific coverage and service boundary

| Backend | Local installation evidence |
| --- | --- |
| Codex | Effective command or `codex`, regular executable and recognized launcher interpreter |
| Cursor | Effective command or `cursor-agent`, same checks; no mandatory separate Node if distribution bundles it |
| Kimi | Effective command or `kimi`, same checks using its actual ambient/constrained environment rule |
| OpenCode managed | Effective CLI command from the other change's launch plan, same executable/interpreter checks |
| OpenCode external | not_required; no CLI lookup, spawning or filesystem runtime requirement |
| ZCode | Effective command or `node`, readable runtime bundle, required structural discovery, and readable built-in provider configuration at effective ZCODE_BUILTIN_PROVIDER_CONFIG_FILE or ../config/provider/zcode-builtin.json relative to the runtime bundle directory |
| fake | not_required; no filesystem or network checks |

For ZCode, a nonempty ZCODE_BUILTIN_PROVIDER_CONFIG_FILE is the provider-config override; a relative override resolves against the effective workspace. With no nonempty override use ../config/provider/zcode-builtin.json relative to the resolved bundle directory. Add a probe-only entry to the embedded host that stops after read/discover and provider-config existence/readability checks, before `_compile`, lazy thunk execution, account files, native credential access or child app-server spawning. Run only this bundled probe with the resolved Node executable; do not execute the desktop bundle. Resolve all installation inputs from the effective launch environment, but run the inspector with a minimal explicit environment that retains only needed path/OS values and omits Node preload hooks such as NODE_OPTIONS; the inspector receives resolved runtime/config paths as arguments. This is an inspection-only environment restriction, never a change to the eventual backend child environment. Configured executables are trusted local programs, not a sandbox boundary. Missing Node and missing runtime/config are independent issues and both are reported; structural discovery is blocked by missing Node/runtime and does not generate duplicate derivative errors. Keep the existing structure-based compatibility test and fingerprint, not an exact version/hash allowlist. Normal launch retains its own compatibility/account checks. Personal provider/account files and auth-dependent runtime behavior stay outside installation preflight. The default runtime path remains macOS-specific; Linux requires explicit runtime_path. Native Windows local backend checks return unsupported_platform in source builds, before applying Unix permission logic; fake and external mode need no local executable. This change does not certify the rest of Squad on Windows. WSL uses Linux rules.

Preflight has two stages: (1) collect *all* local installation results; (2) only if stage 1 succeeds, ask OpenCode's lifecycle integration to ensure managed services and check HTTP readiness for each used service configuration. Installation checks themselves never start a managed server. Stage 2 may start an owned managed server but cannot create conversations or submit prompts; all required services must be ready before any agent work. Failed startup cleanup belongs to the existing supervisor. Once startup succeeds, the server belongs to Squad even if the admission later fails or its caller cancels; keep it until Squad shutdown, never stop it as per-request cleanup. Never terminate an external server. Effective snapshot/config verification remains mandatory under opencode-runtime, with its existing bounded config request, before session creation or work.

External readiness uses bounded GET `/global/health`, requires 2xx JSON with healthy:true; version is optional informational metadata and is not a gate, with redirects disabled. Unreachable/non-2xx is service_unavailable; malformed or unsupported health shape is service_incompatible. This verifies the minimal health protocol, not model support or the entire API version. Managed readiness uses the existing lifecycle hook with the same healthy:true predicate. This change does not tighten that hook to require version. A failed initial managed start (including initiating cancellation or timeout) and a dead owned child remain latched until explicit Squad restart. Preserve the immediate cause code (start_failed, timed_out or cancelled), attach restart_required:true, and say "Restart Squad explicitly after correcting the cause." Subsequent checks of that runtime return restart_required without another launch. Stage-1 failures and external service failures do not set this latch. A request rejected before commitment retains its request ID, but retrying it cannot clear a runtime latch. Do not invent an exact supported version range. Separate `phase: readiness` from `phase: installation` in reports and point service errors at official server docs instead of telling external users to install a local CLI. Endpoint/proxy routing and authentication use the other change's transport; credentials and raw response bodies never enter diagnostics.

### 4. Selection and aggregation

For new workflow admission, select all agents referenced anywhere in the definition, including downstream/loop tasks and allowed_to_fail tasks; graph position is not a reason to defer a prerequisite. For recovery/resume select all agents that can still execute: unresolved tasks plus tasks in any unfinished enclosing loop that may re-arm, excluding permanently completed workflow-scope tasks and done root subtrees. Conservative inclusion inside unfinished loops is intentional. Retry acceptance checks only the retry target, including its service readiness. Unrelated installation/loop holds cannot reject an otherwise eligible retry; they remain dispatch gates. Target-only success clears at most issues attributable solely to that target, never an execution-wide aggregate or unrelated issue. Manual admission selects only the named agent. Configuration entries and machine sections that are unused never block work. No new enabled flag is introduced; if a later change adds one, selection follows its admitted graph, never raw disabled entries.

Deduplicate within one pass by an internal canonical key of backend, mode, effective command/runtime/dependency settings, absolute workspace, and full effective child environment (plus service configuration for readiness). Exclude agent name, prompts and model/reasoning, which are not installation requirements. Different explicit paths remain separate even if symlinks target the same file. Full environment comparison is conservative and avoids unsafe merging of wrappers influenced by env. Keys and their values are memory-only, never logged or persisted; use collision-safe equality if hashing. Treat absent versus empty environment values distinctly; canonicalize environment keys with the existing last-effective-value semantics. No global cache or persisted success bit. Aggregate each issue with all affected names; order phase, backend, agent list, component, code deterministically.

Stage 1 has a 30-second aggregate budget, including local probe cleanup, with five seconds per unique local check and at most four concurrent checks. Only after it passes does stage 2 receive a separate 60-second budget, including managed failure cleanup: the existing 30-second managed startup and up-to-10-second effective-config request are not charged to stage 1. Each standalone service health request has a five-second deadline; the supervisor retains its shorter internal polling timeout. Total normal pass bound is 90 seconds, subject to earlier caller deadline/cancellation. Keep capacity for the one shared managed startup immediately at stage-2 entry; external checks may run alongside it up to the concurrency bound.

An earlier caller or phase deadline can still cut a managed start short: report timed_out (cancelled for explicit cancellation) plus restart_required:true if the supervisor has latched failure. Once successfully started, later config/health timeout does not reset/stop the server or manufacture a startup latch. Inspect supervisor state rather than inferring the latch from an arbitrary timeout. Completed errors remain in the report; mark unfinished groups explicitly. Bounded cleanup may finish after caller cancellation, within the phase cleanup budget, without admitting any work. A disconnected caller gets no fabricated HTTP response.

Bound probe output to 64 KiB, suppress raw output and join descendants. Context-aware I/O must return by deadline; uninterruptible kernel filesystem I/O is a documented host limitation. No cross-pass cache: batch cost is bounded by selected ready groups, deduplicated within the pass. Record timing in tests so repeated loop batches can be assessed without relaxing freshness.

### 5. Integration and lifecycle serialization

- Keep config.Load/NormalizeAgentOptions/ValidateWorkflowDefinition and machine YAML parsing structural. No config-path side effects, searches or network calls. There is no existing validate CLI; do not add one just for this change.
- In orchestrator.New register metadata and restore state without external session creation. Defer external Init/Recover until a selected admission passes. Agent enumeration remains available with idle/restored metadata. Reset clears local session identity, and force reset still cancels/joins existing work; defer replacement external session creation to the next checked turn. Backend session IDs and startup-prompt behavior are preserved for ordinary repeated turns.
- Add an orchestrator preflight entry used by the workflow Executor boundary. Add context to Manager.Create/Resume/Retry and corresponding API interface methods; requests supply r.Context(), recovery supplies the server context. Controls that only change loop intent do not launch anything directly; all newly released work goes through the dispatch gate.
- Create: perform validation, idempotency and conflict checks first. Reserve admission in memory under the manager mutex, capture definition/revision/config, release the lock for preflight, then reacquire and revalidate reservation/state/caller context before committing the first execution snapshot/request record. Failed preflight releases reservation and consumes no request ID. Concurrent competing requests retain 409 semantics; an identical in-flight request waits with its own context and then replays the committed result or receives the failed admission report. Cancelling a waiting duplicate does not cancel the owner.
- SubmitRun: similarly reserve the selected agent as admitting under its lock, perform preflight outside the lock, revalidate before allocating/persisting a run or appending facilitator_message, then initialize/use its session and launch. Other operations see busy/conflict; forced reset or shutdown invalidates the reservation and cancels its preflight. No broad orchestrator mutex is held during probes.
- Recover: repair interrupted state/artifacts first. There can be at most one nonterminal saved execution; reject two or more as existing corruption before any preflight. Terminal history is not checked. Bind/start the API listener before scheduling recovery preflight, with an in-memory dispatch gate closed until completion; expose backend_preflight.status=checking without persisting a new execution state. Start returns after structural recovery, not after slow probes, and shutdown cancels/joins the recovery check. This requires splitting structural recovery from asynchronous environment checking in both serve and the one-shot bootstrap. Before opening the recovery dispatch gate, preflight eligible remaining agents. On failure persist needs_attention and sanitized report, keep the original mode/pause intent and other causes, and start the API without dispatch. Terminal/cancelling executions do not need installation. Paused executions are inspected without installation; resume performs the check. Existing judging-only recovery remains permitted because it is not backend installation work; CheckInstallation never invokes the judge.
- Resume performs the remaining-agent pass; an eligible new Retry checks only its target before committing its retry record. A queued retry still waits for every unrelated attention/dispatch gate. Accepted idempotent retry replays do not recheck. A full successful pass removes backend_preflight causes; target-only success removes only independently attributable target issues and leaves the aggregate cause while any issues remain; uncertainty, cleanup, artifacts and all existing loop gates remain. Failed retry/resume retains pending state and returns 503.
- Each scheduling batch preflights all ready candidates outside the manager mutex before durable attempt reservation. Revalidate snapshot revision and gates on return; stale results cannot launch work. On any failure hold the execution, reserve no new attempts, and allow already running work to settle. SubmitOwnedRun also checks its selected effective adapter before Init for direct callers; the scheduler may hand it an unexported, single-dispatch prepared plan to avoid repeating the same immediate check. No reusable success token is exposed to HTTP or persisted.
- Disappearance after a successful check is still possible. Actual spawning uses the resolved executable, preserves launch errors and existing failed/interrupted attempt semantics, and never silently falls back or retries work. Session continuity is independent of installation check results.

### 6. Error and persistence contract

HTTP installation/readiness rejection is 503 with `error` (concise aggregate text), `code: backend_preflight_failed`, and `issues` entries containing phase, backend, agents, component, code, restart_required, message, installation_links (array of label/url). Caller cancellation returns context.Canceled internally. For a disconnected/cancelled HTTP request, stop processing without writing a synthetic error response (no 408 or custom 499 contract). Retain sanitized cancellation/latch diagnostics for existing execution views; a later live request against a latched managed runtime receives ordinary structured 503. Deadline expiry is 503 with timed_out issues. Existing malformed request 400, unknown identity 404, conflict 409 and unexpected storage/internal error 500 remain unchanged.

Codes: not_found, not_executable, not_readable, invalid_search_path, unsupported_launcher, unsupported_runtime, unsupported_platform, timed_out, cancelled, check_failed; readiness also service_unavailable/service_incompatible/start_failed/restart_required. Every issue carries restart_required (boolean); true is reserved for runtime conditions requiring explicit Squad restart. Human messages use fixed templates, backend/component and agent names; they do not include raw command/path option values, environment, URL userinfo/query, PATH contents, credentials or child output. Failure to locate a command names its option source (agent command, machine command or built-in default) and tells the user to inspect effective PATH, without printing its value. Built-in command names may be shown; arbitrary configured basenames remain omitted because they can contain credentials. This is a narrower public-preflight policy than backend-config's permission to expose operational paths, not a prohibition on existing invocation provenance. Follow this guidance with one short installation link per relevant product; ZCode can include Node and desktop links. No scripts or long instructions in reports.

Existing executions add optional sanitized `backend_preflight` report data to snapshot and view, plus `backend_preflight_failed` in AttentionReasons. This is diagnostics, not admission authority; absence in old snapshots means unchecked, and success is never persisted as reusable evidence. Existing schema numbers/definition hashes stay unchanged. Clear this report/cause only after a full successful fresh pass; target-only success can clear only independently attributable target issues. Store errors remain fatal/holding under existing rules. `serve` on a new squad does not demand every backend installation; recovery installation holds keep it running. Actual startup errors still use the existing CLI exit 2. For run, a pre-selection installation/readiness rejection exits 2 after cleanup, prints the same concise aggregate with links to stderr, and emits the existing version-1 JSON summary with null execution identity/state and no workflow summary file; do not print usage. Once an existing execution is selected, an installation hold is needs_attention: keep the API/process alive for repair/resume or cancellation. Terminal replay performs no installation checks. Existing terminal/signal/cleanup exit mappings and JSON schema remain; cleanup/reporting failure overrides with exit 1. Carry attention/restart guidance through existing summary attention/error fields.

## Risks / Trade-offs

- [A file check is not a successful model run] → explicitly exclude authentication, model support, arbitrary wrappers and late dynamic loader failures; keep launch-time error handling.
- [PATH correction breaks configurations relying on accidental ambient lookup] → document inherit_env: [PATH] or absolute command and test both; never widen constrained environments silently.
- [Slow mounts and bundle scanning] → deadlines, bounded concurrency/output and no persistent cache; acknowledge kernel-I/O cancellation limits.
- [External health success does not prove every endpoint compatible] → name the minimal check precisely and retain real request errors.
- [Admission refactoring races with reset/cancel/recovery] → short reservations, context propagation, revision checks, meaningful race tests; no I/O under global locks.
- [OpenCode work lands separately] → wire its resolved plan and lifecycle hooks only after that contract exists; do not duplicate supervisor, proxy or snapshot logic.

## Migration Plan

Implement against the OpenCode mode/lifecycle contract, update all adapters/test doubles, then activate orchestration/API gates together. No user data migration or new YAML keys are needed. Document the earlier HTTP 503 and effective-PATH lookup changes. Existing saved runs and session IDs remain usable; old snapshots get a fresh check. Rolling back removes early checks and returns to late launch failures; optional diagnostic fields can be ignored by older readers but installation holds may require explicit resume after repair. Never rewrite or delete completed attempts to clear a hold.
